## Task 1 - Build the Network (15)

tasks: [1]
objective: Build the network with the lab script, then inspect what it built and bring up the ONOS controller and the Open vSwitch fabric.

### Evidence

- Network built with `ducky.sh build` and the specified WAN address
- ONOS web interface reached and logged into
- The five-switch spine-leaf fabric identified in the topology viewer: spine1, spine2, leaf1, leaf2, leaf3
- Each leaf shown with one link to each spine, and the spines connecting only to leaves
- Each Ubuntu-CLI host's address and default route recorded
- One Word document submitted, with CLI output and captures in fixed-width type

### Critique

- Topology described without naming the specific switches or their links
- Host addressing or default routes omitted
- Build output pasted with no inspection or discussion
- CLI output not in fixed-width formatting

## Task 2 - Reactive Forwarding (15)

tasks: [2]
objective: Demonstrate a network that forwards everything while the reactive forwarding application runs.  Describe the relationship of real world traffic to the follows in the controlled network.

### Evidence

- Active ONOS applications listed from the CLI (`apps -s -a`)
- A successful ping from each Ubuntu-CLI host to the other two hosts
- A successful ping from each Ubuntu-CLI host to 8.8.8.8
- Hosts shown on the ONOS topology map in the web interface
- Hosts and flow rules listed from the ONOS CLI (`hosts -s`, `flows -s`)
- The relationship between the pinged traffic and the installed flow rules explained

### Critique

- Pings shown for only one or two hosts instead of all three
- Flow rules listed with no connection drawn to the observed traffic
- Application list omitted
- Topology map screenshot missing the hosts

## Task 3 - Move to Intent Based Flows (25)

tasks: [3]
objective: Demonstrate fowarding with flows instead of generic ethernet forwarding.  Analyze the difference between flows and intents.

### Evidence

- Reactive forwarding application deactivated (`app deactivate org.onosproject.fwd`)
- The repeated pings shown failing after deactivation
- Hosts listed from the CLI with their host IDs
- A host-to-host intent installed between Ubuntu-CLI-1 and Ubuntu-CLI-2
- The installed intent listed and connectivity to Ubuntu-CLI-2 and 8.8.8.8 restored
- A second host-to-host intent installed between Ubuntu-CLI-1 and the VyOS-1 fabric address, and listed
- Flow rules on each switch listed and compared against the installed intents

### Critique

- Ping failure after deactivation never shown
- Only one of the two intents installed or verified
- Intents listed but never tied to the restored connectivity
- Flow rules shown with no comparison to the intents that produced them

## Task 4 - Link Failure (25)

tasks: [4]
objective: Demonstrate how an installed intent responds to the loss of a link. Describe what the ping does and what ONOS changes in the flow rules.

### Evidence

- A continuous ping running from Ubuntu-CLI-1 to Ubuntu-CLI-2
- The intent's path shown on the ONOS topology map (hosts and device labels visible)
- The specific spine the path crosses identified (of:...11 as spine1 or of:...12 as spine2)
- The link between leaf2 and that spine taken down from the Mininet CLI
- The effect on the continuous ping observed and described
- Intents and flow rules listed again after the link goes down, showing the change
- The link brought back up and the Mininet session exited cleanly

### Critique

- Ping behavior during the outage not described
- The crossed spine never identified
- Intents or flows checked only before the failure, not after
- Link left down, or the Mininet session left open
