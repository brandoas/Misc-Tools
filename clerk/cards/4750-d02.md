## Report Standards (5)

objective: Present the evidence to the Lab Report Guidelines: one Word document, a drawn diagram, fixed width for CLI output and captures only, and every block of output attributable to the command and the router that produced it.

check 1: single_docx
check 3: terminal_text_formatted

### Evidence

- One Word document
- Hostnames set and visible in the CLI output, so output can be attributed to a device
- Fixed width type used for CLI output and captures, and only for those
- Route tables readable, not wrapped into unreadable lines
- Every block of output tied to the command and the router that produced it

### Critique

- Output from an unnamed router, which cannot be attributed with five near identical devices
- Route tables line wrapped into illegibility
- Packet or route data pasted with no command shown

## Task 2 - Static Routing Deployment (10)

tasks: [2]
objective: Demonstrate a working Statically routed version of the lab.

### Evidence

- Every router pings every other router's loopback, in both address families
- `show ip route` shown on each of the five routers
- `show ipv6 route` shown on each of the five routers
- Both address families present throughout, not one only

### Critique

- One router's route table offered where the task asks for each
- Only one address family proven
- A reachability failure left unresolved at this stage, which OSPF will later mask

## Task 3 - OSPF Recipe Design (10)

tasks: [3]
objective: Design and document the OSPF configuration for this lab.

### Evidence

- All static routes removed except the default route on VyOS-1 to the internet
- Loopbacks configured in both families on every router
- OSPFv2 router ID set explicitly from the Task 1 design
- One OSPFv2 network statement per interior block, and none for the WAN
- `network point-to-point` on every infrastructure interface
- `passive` on every client LAN interface
- `default-information originate` on the edge router only
- OSPFv3 enrolled per interface, with no network statement
- `lo` listed explicitly in the OSPFv3 enrolment

### Critique

- Interior static routes left in place, which makes Task 4 appear to work while proving nothing about OSPF
- The WAN included in an OSPF network statement
- `default-information originate` on more than one router
- A `network` statement written for OSPFv3, which has none

## Task 4 - OSPF Deployment and Verification (25)

tasks: [4]
objective: Apply and demonstrate the functionality of the OSPF IGP.

### Evidence

- Neighbours shown in `Full` state on every transit link, in both families
- Nets 1 to 3 show no neighbours, because those interfaces are passive
- Every router's loopback /32 appears in every other router's table as an intra-area route
- Transit links show as point-to-point with no DR or BDR elected
- Neighbour counts match between IPv4 and IPv6
- Traceroutes from each of the three client computers to the other two, six in total

### Critique

- Anything short of `Full` presented as working
- Neighbours present on Nets 1 to 3, meaning the interfaces were never made passive
- Loopbacks appearing as external or inter-area, meaning redistribution was used instead of enrolment
- A DR or BDR elected, meaning the network type was left at broadcast
- A partial set of traceroutes at item 28

## Task 5 - Link-Failure Analysis (10)

tasks: [5]
objective: Demonstrate and explain the operation of OSPF during a network failure.

### Evidence

- Traceroute from Ubuntu-CLI-1 before the link is suspended
- Traceroute from Ubuntu-CLI-1 after the link is suspended
- The specific hop that disappeared is identified
- The alternate path OSPF selected is traced through the diagram
- The student states that reconvergence happened with no human reconfiguration

### Critique

- Two traceroutes pasted side by side with "the path changed" and no analysis
- The changed hops never identified
- No connection drawn back to the static routing of Task 2
- The link left suspended rather than resumed

## Task 6 - Thought Questions (15)

tasks: [6]
objective: Answer the two thought questions: how OSPF detects and repairs a broken network, and three routing protocols VyOS supports other than OSPF and BGP.  (DERIVED: the handout states no Objective for Task 6)

### Evidence

- Failure detection described via the hello interval
- The dead interval described
- Flooding of the updated link-state advertisement described
- Every router recalculating shortest paths from the updated database
- Three routing protocols named from the valid set, excluding BFD, Failover, Multicast, MPLS, IPv6 Multicast, RPKI and ARP
- All three verbs answered for those protocols: explained, compared and contrasted
- When and why each would be used

- An answer that stops at "it notices the link is down", which is a third of the question
